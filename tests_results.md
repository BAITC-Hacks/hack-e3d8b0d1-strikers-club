# Результаты проверки backend по пользовательскому тестовому набору

Дата: **23 сентября 2026**, часовой пояс Asia/Qyzylorda (UTC+5). Отчёт собран 17:53.
Основание: [ekt-test-scenarios.pdf](tests/ekt-test-scenarios.pdf), версия 1.0, 12 страниц, восемь отдельных вложений. Проверялась текущая рабочая версия поверх коммита `62e34b7`, включая реализованный multipart `file + message`.

## Итог

**В текущем запущенном окружении ни один из восьми сценариев загрузки не доходит до содержательного ответа:** два XLSX возвращают `422 invalid_attachment`, остальные шесть файлов — `503 upload_scanner_unavailable`.

**После подключения настоящего ClamAV только в отдельном тестовом экземпляре: полностью пройден 1 из 8 сценариев — №08; семь не пройдены по функциональным критериям PDF.** №04–07 возвращают HTTP 200, но содержат существенные расхождения. №03 завершается HTTP 502; №01–02 остаются HTTP 422. Один HTTP 200 не считался прохождением сценария.

**Критический дефект корзины:** фраза «Нет, не добавляй» не отменяет активное предложение, хотя текст ответа утверждает обратное. Следующее «да» добавляет 3 шт. Ошибка воспроизведена дважды в разных новых сессиях. Обычное подтверждение и повторы без дублирования работают.

- 199 автоматических тестов проекта прошли; Ruff, mypy и проверка форматирования прошли.
- Все восемь файлов побайтно совпадают со вложениями внутри PDF-руководства.
- Все восемь файлов отдельно проверены настоящим ClamAV: угроз не обнаружено. Это результат проверки данным сканером, а не гарантия отсутствия любых угроз.
- Во всех восьми сценариях загрузки корзина осталась пустой.
- Исходники backend, `.env` и исходные вложения в ходе проверки не исправлялись. Этот отчёт фиксирует обнаруженные проблемы.

## Методика и границы проверки

1. Прочитаны все 12 страниц руководства. XLSX/DOCX разобраны локально по ZIP/XML, текстовый PDF — по текстовому слою; скан и две фотографии просмотрены визуально. Независимо от этого выполнено реальное распознавание через backend для файлов, прошедших его фильтр.
2. Восемь исходных файлов отправлены в работающий `http://localhost:8000` через multipart с точными сообщениями из PDF. Для каждого создана отдельная сессия; `GET /api/cart` вызван до и после загрузки.
3. Затем тот же код запущен в одноразовом Docker-контейнере с `UPLOAD_SCAN_HOST=clamav` и отдельным префиксом Redis. Использованы реальные OpenAI, EKT, Redis и ClamAV, без подмены их ответов. Основной контейнер и `.env` не перенастраивались. Тестовый префикс Redis удалён после завершения.
4. Три контрольные карточки дополнительно запрошены напрямую через EKT detail API. Отдельная локальная диагностика поиска использовала эти реальные снимки карточек с подменённым индексом; она явно не считается внешним end-to-end тестом.
5. Ветки корзины проверены на работающем API в новых сессиях. Предусловие «после успешного вложения» в основном окружении невыполнимо из-за блокировки uploads, поэтому корзина дополнительно проверялась текстом из PDF, без предзаполнения данными вложения.
6. Согласие на отправку восьми учебных файлов в OpenAI и данных в EKT получено отдельно перед внешним прогоном. Ключи, токены сессий и служебное зашифрованное содержимое модели в отчёт не включены.

Перед полным прогоном принят диагностический порог **10 секунд до содержательного ответа на вложение**. Это выбранный для отчёта порог, а не согласованный SLA. Быстрые ответы с ошибкой не считаются успешными. Каждый файл проверен одним полным внешним запросом; это не нагрузочный тест и не оценка статистической стабильности LLM.

Проверка detail API: 2026-09-23T12:44:41.350160+00:00. Цены всех трёх товаров совпали с учебным снимком. Для `200300282_` и `RM17UAS16` в PDF остатки были неизвестны, но текущий API вернул соответственно **19** и **0**. Это изменение/уточнение источника, а не ошибка backend. Ноль — известное отсутствие, не неизвестное значение. Корректный ответ должен различать учебный снимок и свежий API.

По текущим данным запрос №02 на 24 штуки `027228 → 200300285_` превышает общий остаток 23 на одну штуку. Запрошенные 24 нельзя молча заменить на 23. У реле текущий остаток 0, поэтому нельзя сообщать, что оно доступно.

### FAIL: отказ не отменяет предложение

На точную фразу из PDF «Нет, не добавляй» получен текст:

> Понял, не добавляю. Предложение отменено; корзина не изменена.

При этом тот же ответ содержит `pending_cart_action.status="WAITING_CONFIRMATION"` с прежним `operation_id`. Следующее отдельное «да» вернуло `cart_changed=true`, `total_quantity=3`, `total_amount="194760"`. Это не только неверная формулировка ответа: сервер выполнил ранее отвергнутую операцию.

Независимый повтор воспроизвёл тот же переход: предложение — 28.088 с, отказ — 1.556 с, позднее «да» — 0.119 с, корзина **0 → 3**. Текстовый отказ нельзя считать выполненным по одному полю `message`.

Причина: [app/services/chat.py:179](app/services/chat.py#L179) распознаёт отмену только для `нет`, `отмена`, `не надо`. Нормализованная строка `нет не добавляй` не попадает в этот набор и передаётся LLM; инструмент отмены состояния в этом ходе не вызывается.

### PASS: подтверждение и повтор не дублируют добавление

В отдельной новой сессии предложение оставило корзину пустой. «Да, добавь» добавило ровно 3 шт. на 194 760 ₸. Повтор той же фразы не добавил ничего; повтор кнопки с тем же `operation_id` вернул HTTP 200 и текущую корзину с теми же 3 шт. и суммой. Ветка успешного подтверждения пройдена.

Дополнительное наблюдение: один ответ предлагает пользователю фразу «Подтверждаю 3 шт.», которой нет в детерминированном шаблоне `_confirmation`. Эта конкретная фраза отдельно не отправлялась; это статически выявленное несоответствие текста подсказки поддерживаемым командам. ### Локальное воспроизведение ошибки фильтрации

На уже полученной настоящей карточке `515291` вызван действующий `CatalogService.search`. Индекс и повторное чтение detail в этой диагностике подменены сохранённой карточкой, поэтому влияние сети и полноты каталога исключено:

| Параметры search | Полученные ID |
| --- | --- |
| {"article": "200300285_"} | ['515291'] |
| {"article": "200300285_", "brand": "Legrand"} | [] |
| {"article": "200300285_", "category": "Автоматический выключатель"} | [] |
| {"article": "027228"} | [] |

Реальное `TORGOVAYA_MARKA=Legrand` остаётся атрибутом `torgovaya_marka`, но не заполняет `Product.brand`. `OBYEM=Автоматический выключатель` не заполняет категорию; `NOMINALNYY_TOK`, `KOLICHESTVO_POLYUSOV` и другие технические ключи не приводятся к каноническим именам. Извлечение добавляет brand/category/attributes одновременно, и такие фильтры отбрасывают точное совпадение артикула. Это подтверждённая причина пустого поиска; утверждение, что контрольных товаров вообще нет в магазине, неверно.

Цены, общие остатки и склады нормализуются правильно во всех трёх detail-карточках. Ошибка относится к идентификации, фильтрации и передаче контекста, а не ко всем полям каталога.
