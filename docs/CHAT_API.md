# Чат ekt.kz: запуск и контракт API

Backend реализует текстовый чат, временную историю, вызовы инструментов каталога,
подбор аналогов, условия покупки, изображения/документы и подтверждение
демонстрационной корзины.

**Для frontend-разработчика:** [подробное руководство интеграции](FRONTEND_INTEGRATION.md)
с контрактами ответов, сценариями UI, ошибками и TypeScript-клиентом через BFF.

## Настройка

Добавьте в существующий `.env`, не перезаписывая `API_KEY`:

```env
OPENAI_API_KEY=<ваш ключ OpenAI>
OPENAI_MODEL=gpt-5.6-luna
OPENAI_REASONING_EFFORT=low
EKT_API_USER=<Basic Auth пользователь партнёра>
EKT_API_PASSWORD=<Basic Auth пароль партнёра>
EXTERNAL_SEARCH_ENABLED=false
```

Все необязательные настройки и лимиты находятся в `.env.example`. API_KEY,
OPENAI_API_KEY и EKT_API_PASSWORD — разные секреты. Не отправляйте их в чат.

```bash
COMPOSE_BAKE=false DOCKER_BUILDKIT=0 docker compose up --build -d
```

Без внешних ключей создание сессий работает при настроенных API_KEY и Redis;
запрос к ненастроенной интеграции
возвращает `503 integration_not_configured`. Backend не подменяет реальные
внешние сервисы демоданными. Модель можно переопределить через `OPENAI_MODEL`;
по умолчанию сохранена модель из ТЗ.

## Авторизация

Все chat/cart/products маршруты требуют `X-API-Key`. Это ключ доверенного
backend-клиента, его нельзя встраивать в публичный JavaScript. Для сайта
используйте серверный прокси/BFF с пользовательской авторизацией.

`POST /api/chat/sessions` создаёт новую сессию и один раз возвращает
`session_id`, `session_token`, `expires_in`. Для последующих chat/cart запросов
передавайте токен в **X-Session-Token**, не в URL. Знания одного session_id
недостаточно. Redis хранит только SHA-256 токена. По истечении сессии создайте новую.
Автоматический обмен анонимного браузера на токен/HttpOnly-cookie относится к BFF.

```bash
# API_KEY задайте в окружении терминала тем же значением, что в .env.
curl -X POST http://localhost:8000/api/chat/sessions \
  -H "X-API-Key: $API_KEY"

# Подставьте session_id и session_token из ответа.
SESSION_ID='<session_id>'
SESSION_TOKEN='<session_token>'

curl -X POST http://localhost:8000/api/chat \
  -H "X-API-Key: $API_KEY" -H "X-Session-Token: $SESSION_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"session_id\":\"$SESSION_ID\",\"message\":\"Найди кабель ВВГнг 3x2.5\"}"
```

## Маршруты и ответы

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/chat/sessions` | новая временная сессия |
| POST | `/api/chat` | `{session_id, message}`; текст, поиск, подтверждение |
| POST | `/api/chat/upload?session_id=...` | файл в сыром теле запроса |
| GET | `/api/products/{product_id}` | свежая официальная карточка товара |
| POST | `/api/cart/items` | подтверждение кнопкой |
| GET | `/api/cart?session_id=...` | демонстрационная корзина сессии |

Ответ чата содержит:

- `session_id`, `message`, `cart_changed`;
- `products`: валидированные данные EKT; неизвестные цена/остаток равны `null`;
- `analogs`: серверная оценка, совпадения, отличия, неизвестные параметры;
- `external_variants`: внешние источники отдельно от каталога, всегда требуют проверки;
- `pending_cart_action`: предложение с operation_id, товаром, количеством,
  проверенными ценой/остатком и сроком действия;
- `cart`, `cart_url`: результат подтверждения, если оно выполнялось;
- `extracted`: наблюдаемые идентификаторы из вложения и confidence;
- `demo_cart: true`.

`message` экранирован для HTML. Структурированные поля карточек — данные;
frontend должен выводить их через textContent/обычный React-текст, не innerHTML.
Цены передаются строками Decimal. Остаток может быть дробным; добавляемое количество
в этой версии — положительное целое. Вложения не сохраняют исходное имя в истории.

`GET /api/products/{product_id}` нужен для кнопки «Подробнее» или явного обновления
карточки. Используйте `id` из `products`/`analogs[].product`, а не артикул.
Детали всегда запрашиваются свежими; query-параметра `fresh` нет. Для первичного
показа достаточно карточек из ответа чата. Сессию этот маршрут не продлевает и
не требует `X-Session-Token`.

Маршруты `/api/items` удалены. `/api/cart/items` сохранён как подтверждение корзины.

## Предложение и подтверждение

LLM может только подготовить предложение через `prepare_cart_addition`.
Инструмента изменения корзины в списке LLM нет. Текстовое подтверждение сервер
распознаёт до обращения к OpenAI. Фраза «интересует товар» сама корзину не меняет.

| Запрос при активном предложении | Поведение |
|---|---|
| `да`, `да, добавь`, `добавь` | подтверждение текущего товара и количества |
| `да, добавь 5` | если количество изменилось — новое предложение, затем новое подтверждение |
| `нет`, `отмена`, `не надо` | отмена |
| `добавь другой товар` | отмена старого предложения и новый поиск |
| `да` без предложения | уточнение, корзина не меняется |
| новое вложение | старое предложение отменяется, автоматического добавления нет |

Для кнопки используйте **ровно** значения последнего `pending_cart_action`:

```json
{
  "session_id": "UUID сессии",
  "operation_id": "UUID предложения",
  "product_id": "515291",
  "quantity": 2
}
```

Отправка: `POST /api/cart/items` с обоими заголовками авторизации. Цена от клиента
не принимается. На подтверждении снова запрашивается detail API и учитывается
количество уже в корзине. Если цена изменилась или остатка недостаточно, ответ
имеет `status: reconfirmation_required`, `success: false` и новое предложение,
если доступное количество позволяет. Автоматической подмены количества нет.
Повтор с тем же operation_id и тем же телом возвращает текущую корзину и не
добавляет ещё раз. Иной товар/количество с использованным operation_id отклоняется.

Официальный cart endpoint партнёра не предоставлен. Корзина **только демонстрационная**,
хранится в сессии и не создаёт заказ, не резервирует склад и не меняет ekt.kz.
`cart_url` ведёт к защищённому API этой корзины и требует заголовков авторизации.
Исторические цены не фиксируются как чек: при следующем подтверждённом добавлении
в ту же строку используется актуальная подтверждённая цена.

## Вложения

Принимаются JPEG, PNG, PDF, DOCX и XLSX, до `MAX_UPLOAD_MB` (по умолчанию 20 МБ).
В `.env` добавьте `UPLOAD_SCAN_HOST=clamav`, затем запустите профиль:

```bash
COMPOSE_BAKE=false DOCKER_BUILDKIT=0 docker compose --profile uploads up --build -d
```

ClamAV требует примерно 3–4 ГБ RAM и время на загрузку сигнатур;
[официальные требования](https://docs.clamav.net/manual/Installing/Docker.html).
Профиль не публикует порт сканера. Его временные файлы размещаются в tmpfs;
база антивирусных сигнатур не содержит пользовательских документов.
Пока сканер не готов, uploads возвращает `503 upload_scanner_unavailable`.
Текстовый чат работает без сканера. Можно указать свой ClamAV INSTREAM host/port.

```bash
curl -X POST "http://localhost:8000/api/chat/upload?session_id=$SESSION_ID" \
  -H "X-API-Key: $API_KEY" -H "X-Session-Token: $SESSION_TOKEN" \
  -H 'X-Filename: specification.pdf' -H 'Content-Type: application/pdf' \
  --data-binary @specification.pdf
```

Это **raw body**, не multipart. Такой контракт исключает запись UploadFile/spool
на диск. Для DOCX/XLSX используйте соответствующий MIME из Swagger. Проверяются
расширение, MIME и содержимое, размеры изображения, ZIP/XML-лимиты, запрещённые
внешние связи и активное содержимое, затем антивирус. Файл передаётся в OpenAI
inline; Files API не используется. Извлечение идёт через JSON Schema. Результаты
с confidence ниже 0.65 не становятся подтверждёнными товарами. Артикулы и параметры
проверяются через каталог. Число извлечённых строк ограничено 50; каждая уверенно распознанная позиция
проверяется по каталогу. Общий timeout остаётся ограниченным: для больших
спецификаций делите документ на части, если обработка не укладывается в него.

## Источники и инструменты

EKT API вызывается только сервером через Basic Auth. Пагинация и размер ответов
ограничены. Индекс — Redis TTL 1800 секунд, детали — до 300 секунд. Перед показом
результатов поиска/аналогов и подтверждением корзины детали обновляются принудительно.
Для списков/свойств поддержаны несколько распространённых форм JSON; неизвестная
структура или несовпавший id дают ошибку вместо выдуманного значения.
Лимиты CATALOG_MAX_PAGES/PRODUCTS ограничивают покрытие индекса: настройте их по
размеру реального каталога. Формат реального JSON партнёра требует проверки с его
действующими credentials; автоматические тесты используют контрактные примеры.

Профили восьми категорий находятся в `app/data/category_profiles.json`.
Они расширяются без изменения LLM. Несовпадение обязательного/критичного параметра
исключает аналог; неизвестный критичный параметр требует проверки. Оценка не
сертифицирует взаимозаменяемость. Сложные диапазоны и неизвестные обозначения
сохраняются консервативно, без предположений о совместимости.

Внешний поиск включается `EXTERNAL_SEARCH_ENABLED=true` и разрешён только после
пустого поиска/подбора в каталоге в текущем ходе. Используется Responses web search;
возвращаются только HTTPS-ссылки, присутствующие в источниках ответа. Наличие и
цена EKT для внешних вариантов не заявляются.

Условия покупки находятся в `app/data/purchase_conditions.json`. Пока `approved`
равен false или справочник пуст, помощник предлагает уточнить условия у менеджера.
Вносите только утверждённые партнёром факты, затем пересоберите образ.

## Хранение и ограничения

- БД и постоянных пользовательских файлов нет. История, выбранные товары, корзина
  и идемпотентность находятся только в Redis с TTL.
- Сессия истекает через `CHAT_SESSION_TTL_SECONDS` после последнего успешного
  обращения. История ограничена `CHAT_MAX_MESSAGES`; предложение — максимум 10 минут.
- В Redis не попадают бинарные вложения/base64. Вместо текста файлов в истории
  остаётся отметка `[Вложение]`; ответы с подтверждёнными товарами хранятся по TTL.
- В Responses API всегда `store: false`; история передаётся явно. Серверные
  conversation objects и file IDs не создаются. Это отключает хранение объекта
  response; отдельная политика обработки данных провайдера управляется настройками
  аккаунта: [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).
- Запросы одной сессии сериализуются Redis-блокировкой. Конкурентный запрос получает
  `409 session_busy`. Сохранение проверяет владельца блокировки и существование
  сессии; просроченный процесс не восстанавливает удалённое состояние.
- Общий timeout хода, число tool rounds/calls и размеры HTTP-тел ограничены.
  Ошибка внешнего API откатывает изменения сессии текущего хода.
- `502` означает ошибку внешнего сервиса; `503` — отсутствие конфигурации,
  недоступность Redis или антивируса. Ошибки не содержат ключи или upstream body.
- Платёжных операций нет. Системный промпт запрещает запрашивать платёжные данные.

## Проверки и основные файлы

```bash
python -m pytest -q
TEST_REDIS_URL=redis://127.0.0.1:6379/0 python -m pytest -q
ruff check .
ruff format --check .
mypy app
```

Тесты проверяют Responses tool loop, store:false, историю, авторизацию, подтверждение
текстом/кнопкой, повторы, смену цены/остатка, TTL/конкурентность, нормализацию,
аналоги, malformed responses, сканер и опасные архивы. Вызовы OpenAI/EKT заменены
HTTP mocks; ClamAV INSTREAM проверяется тестовым TCP-сервером. Это не live-проверка
внешних credentials, модели в конкретном аккаунте или актуальных сигнатур ClamAV.
